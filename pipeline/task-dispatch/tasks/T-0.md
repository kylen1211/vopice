# T-0 · 改动前 LLM 行为基线取样(对应原设计表 T-0)

> 本卡的全部内容以 `contract/cases.md` C-17 与 `design.md` 风险节 R-7 为准,本文不复写其定义。

## Interfaces

- **Consumes**
  - `pipeline/task-dispatch/contract/cases.md` C-17:步骤、归档路径、判定口径、"不设自动阈值"的理由。
  - `pipeline/task-dispatch/design.md` 风险节 R-7(坑 P57):为什么必须在任何代码改动之前取样。

- **Produces**
  - `server/evals/baseline_probe.yaml`:固定 8 问场景,judge 只写 `event: response`、不加任何语义判据(C-17 步骤 1 原文)。

## 验收用例

1. **C-17 步骤 1-3**(本卡只做改动前那一轮;步骤 4 的改动后取样归 T-8)。
2. 可执行命令(两个终端):
   ```
   cd /home/ky/git/voice-agent/server && NLTK_DISABLE_IMPORT_SECURITY=1 uv run bot.py -t eval 2>&1 | tee /tmp/pipecat-baseline.txt
   cd /home/ky/git/voice-agent/server && set -a && source .env && set +a && PYTHONPATH="$(pwd)" NLTK_DISABLE_IMPORT_SECURITY=1 pipecat eval run evals/baseline_probe.yaml -v -d --logs-dir eval-runs
   ```
   可证伪期望:第二条命令退出码 0。
3. 归档完备性:`pipeline/task-dispatch/baseline/pre-change-responses.md` 存在且含 8 条编号回复原文,每条能与 `baseline_probe.yaml` 的第 N 问一一对应。判定:`grep -c '^## Q' pipeline/task-dispatch/baseline/pre-change-responses.md` 输出为 8。任一问没拿到 response 不得留空,写明失败原因与原样日志行。
4. 8 问构成按 C-17 步骤 1 原文:2 条知识问答 / 2 条闲聊 / 2 条执行类请求 / 2 条多轮追问。其中 2 条执行类请求在改动前会被 `prompts.py::CAPABILITY_BOUNDARY_SECTION` 拒答——这正是 T-3 改动落地后要对读的核心差异点,必须原样记下拒答措辞。
5. **时序硬要求**(design.md R-7):本卡必须跑在任何一行产品代码改动落地之前。判定:取样时刻执行 `git -C /home/ky/git/voice-agent status --porcelain server/`,输出中不得出现 `server/prompts.py`、`server/bot.py`、`server/config.py`、`server/task_dispatch.py`、`server/task_dispatch_contract.py` 任何一行改动记录;把该命令的原样输出贴进归档文件头部。
