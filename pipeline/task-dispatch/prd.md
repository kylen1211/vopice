## 问题陈述

**核心痛点**:当前 voice-agent 是一个纯"对话者",完全没有"动手做事"的能力——用户交代的任何需要执行动作的请求(调研、编码、多步骤操作等)都无法被处理,这与项目 2 期目标 G3「派活」直接矛盾。

**证据(数据,实查)**:现状盘点核实 `server/bot.py:229-230` 两处 `LLMContext()` 构造均无 `tools=` 参数,全仓无 `register_function`/`FunctionCallParams` 调用点(`codebase-survey.md` K1)——助手当前不具备任何执行类能力,只能"说"不能"做"。

**第一层为什么(直接诉求)**:项目 2 期路线图(证据:决策留痕,`CLAUDE.md`/`capability-ledger.md`,2026-08-02 用户拍板)明确把 G3「派活」列为独立于对话质量(G2)之外的核心能力——助手需要能把用户交代的、适合放到后台执行的事情派出去,而不是让用户在通话里干等一个可能耗时数分钟的同步操作跑完。

**第二层为什么(场景约束,为何不能简单地"同步执行完再答")**:语音通话与文字对话在产品形态上本质不同——聊天场景里"发消息、过会儿再回"是自然的交互节奏;但一通正在进行的语音通话如果因为等待某个动作执行而陷入长时间沉默,用户体验上等同于通话卡死,且用户没有任何"仍在后台工作"的感知渠道。用户本人对此有明确表态(证据:访谈,用户 2026-08-08 原话)——「正常派活不应该影响 主会话,只不过在接到 通知的时候他 得知道怎么说」,并在架构收敛的用户裁决清单里重申"唯一真实设计点:派活不影响主会话,任务通知回流时前台要知道怎么说"。因此"派活不阻塞、不打断对话"不是体验优化项,而是语音这个交互形态下的硬约束。

**第三层为什么(为何是"接入 OpenClaw"而不是"自建编排")**:项目当前完全没有"做事"的能力(K1),若自己从零搭建任务调度、状态机、审批确认链、多渠道通知、人工接管这一整套编排系统,自研量巨大,且与项目纪律"官方脚手架结构不动"、用户口径直接冲突(证据:访谈,用户 2026-08-08 原话——「派活这部分 我们最好使用 原生能力,他们有什么我们就用什么 不需要额外自己研究,我们要参考成熟方案,外部资料也可以作参考但是骨架不要乱改,我们减少自研,目前主agent 派活 子agent 工作按道理是个很成熟的技术」)。本机已有一套满足这整套需求、常驻运行、MIT 许可、文档与源码均可核实的成熟系统——OpenClaw Gateway(证据:数据,`openclaw-reference.md` 一手材料核实:版本 2026.7.1-2、`LICENSE` 实读为 MIT、`docs/`+`dist/` 完整可读、systemd 常驻已在本机运行),已具备任务派发、状态机、审批确认链、多渠道通知、人工接管这五项全部机制,并经架构收敛(`architecture-convergence.md`,用户确认"完美符合需求")定形为唯一路径,自研面收窄到几乎为零。

**谁遇到**:本项目唯一使用者/产品 owner 本人(项目定位:个人 AI 语音助手,单用户场景;证据:`CLAUDE.md` 项目总纲)。

**不解决的代价(假设)**:助手的能力上限被锁死在"仅能对话",无法承接项目 2 期目标里"派活"这个独立能力维度,后续依赖"助手能做事"这一前提的能力(如 G4 页面监控的后续动作)也会失去地基。

### 硬约束处置对照(C1-C5)

- **C1 · `prompts.py` 能力边界段与派活冲突(冲突·最高优先)**:`CAPABILITY_BOUNDARY_SECTION`(`prompts.py:22-29`)现声明"无任何执行类能力,禁止出现已完成/已处理表述",与派活能力直接矛盾,**必须改,不可回避**。但改动**严格限定为最小改动**:仅删除"无执行能力"这一表述本身,使其不再与实际能力矛盾;**不新增任何关于任务状态如何转述的约束或校验**(如"转述须与外部状态一致""不得美化"等)。用户 2026-08-08 两次明确裁决:外部系统(OpenClaw)报什么状态,快脑就转述什么,状态是否真实、描述是否清楚均是 OpenClaw 的责任——「这个我们不管,他说好了就是好了,置于真正是否做好是他的事情,要改的也是他不是我们」「这也是 openclaw的问题 要改也是改他」——不属本项目验收范围,本项目不对转述内容做工程约束或核验。**由此不单列 FR**——本条处置本身即最终处理方式。附带的直接技术后果(非新增需求,只是删除动作的连带影响,记录于此避免遗漏):`evals/r4_no_false_completion.yaml` 现有判据文本("回复明确说明自己没有执行操作的能力")引用了即将被删除的表述,需做最小同步更新以消除对已删表述的引用;更新同样不得引入新的转述内容校验。**本轮复核(2026-08-08,派活 worker 选型定为 `UIWorker` 后)**:前提变化后,快脑仍需要知道自己"可以把事情交出去"(否则不会触发路由决策),但不再需要知道派活的任务规划细节(这层责任已转移给 task-dispatch worker 自带的第二个 LLM,见 FR-1)。**维持原处置,不作调整**——"仅删除无执行能力表述"这一最小改动本身就足以让快脑知道"我能交出去"(删掉的正是一句会与"可以交出去"相矛盾的禁止性声明,删掉即解除矛盾);快脑不需要额外获知"如何交出去""交出去后任务怎么描述"的任何提示词内容,那属于第二个 LLM 自己的推理范围,不经过 `prompts.py` 这份文本。核心裁决(不新增转述内容约束、完成真实性归 OpenClaw)不受影响,不作放宽或收紧。

- **C4 · `on_client_disconnected` 断连即杀 pipeline,与"任务不随对话中断"冲突**:采纳架构收敛纪要的结论——该冲突因架构变化自然消解(任务执行体在另一进程 OpenClaw Gateway,pipecat 的 `worker.cancel()` 够不着它)。置信度约 80%(推理链条清晰——`worker.cancel()` 的调用对象是具体某个 worker 实例,任务执行在 OS 层面独立于 pipecat 进程——但 `external-research.md` §1.6 明确标注"本次调研没有直接的 PoC 验证它",是推理结论不是实测结论)。**反证条件**:若 S2a 阶段验证发现断连后 OpenClaw 侧任务确实被连带影响(例如 `openclaw agent` 是作为 voice-agent 进程的子进程、未脱离父进程组,导致父进程退出信号连带终止子进程),则该处置不成立,需重新设计任务与进程/会话生命周期的隔离方式。FR-1 判据 2 本身就是对这条结论的实测确认,不是重复劳动。
- **C5 · 落地触达 `server/bot.py`,与既有债务 D-002/D-003 同模块重叠**:显式接受、转交下游裁决——是否在本次改动前先偿还 D-003 是技术排期问题,不是产品需求问题,PRD 不拍定,留给 S2a 技术设计阶段判断。本 PRD 只要求新增代码不因"图省事"而进一步扩大该模块现有债务面(如不新增更多模块级副作用导入),这是验收阶段的软约束,由 code-reviewer 在实现阶段核对,不产出独立可证伪判据,**不单列 FR**。

**关于"回退"路径的说明**:本项目在 voice-agent 侧不持有可回退的持久任务状态(呼应 C1 处置与下方非目标#2)——任务的执行、状态、审批记录全部由 OpenClaw 一方持有,voice-agent 只是发起方与播报方,因此不存在"派活相关回退步骤"需要设计。本期语音侧不支持任务取消(见非目标"任务中止/取消"),该口径不受影响——若后续加上取消能力,同样是纯粹调用 OpenClaw 现成的 `tasks cancel` CLI,不引入 voice-agent 侧任何可回退状态或撤销记录。

### 前提假设:OpenClaw 侧权限配置需避免触发运行时审批(环境约束,非 FR)

**背景**:本期(2026-08-08 二次收窄范围后)不做任何审批相关能力(原任务中止/取消、审批请求后台监听、用户口头意见转发为审批裁决、审批超时兜底四条 FR 已整条删除,见非目标)。这之所以能够成立,前提是用户在 OpenClaw 侧把权限配置成**不会在运行时触发审批请求**——这是一个部署/配置层面的前提假设,不是本项目要实现的行为,因此不落 FR,但必须显式写清楚,否则实施时会踩坑:派活任务一旦触发审批,而 voice-agent 侧又没有任何机制去处理/回应它,该审批会按 OpenClaw 默认超时语义 `askFallback` 默认 `deny` 终局拒绝,导致任务失败,且用户在通话中不会得到任何解释。

**已核实的事实(来源:`research/openclaw-reference.md` §1.1-§1.3)**:
- `tools.exec.mode` 五档:`deny` / `allowlist`(只跑白名单,不问)/ `ask` / `auto` / `full`(不问)。配 `full` 或 `allowlist`+预置白名单即可不触发运行时审批。
- `ask` 三态:`off`(从不问)/ `on-miss` / `always`。
- **坑(必须显式知晓)**:策略是多源取严合并,原文"Effective policy is the stricter of `tools.exec.*` and approvals defaults: approvals can only tighten config-derived security/ask, never loosen them"。执行主机本地 approvals 文件能压过配置侧,主机侧 `ask: "always"` 会盖掉配置侧的设置——**只配一处不够,两侧都要配**,否则照样弹审批,并按 `askFallback` 默认 `deny` 超时终局拒绝,任务失败。

**验证方式(前提假设本身的验证,不是 FR 判据,但同样要求可证伪)**:
- 派活前确认有效策略确实不会触发 ask:`openclaw approvals get --json` 可取当前生效策略快照,核对其不处于会触发 `ask` 的档位;或
- 在验收场景中实际派一个会触发 exec 的任务,确认全程无 pending 审批产生——`openclaw tasks show <lookup> --json` 观察其从 `queued`/`running` 直接演进到终态,期间未出现依赖人工处理的中间停滞。

**反证条件**:若验收时发现某类任务仍会触发 pending 审批(如遇到未覆盖到白名单/`full` 档位的工具调用),说明该前提假设未被满足——此时任务会因无人处理审批而按 `askFallback` 默认 `deny` 超时失败,需回头补全 OpenClaw 侧配置(两侧都要配,见上方"坑"),而不是回来找 voice-agent 补审批处理能力(那是本期明确不做、已移入非目标的范围)。

### FR-1 · 派活触发与任务生命周期解耦(快脑路由 + task-dispatch worker 二级决策;不阻塞对话、不因断连中止)(P0)

**描述**:用户明确将派活定性为异步行为(原话:「我们语音是 属于派活 而且可以是 异步」)。**两级决策分工**(官方 delegation 模式,源码实锤见 `research/pipecat-worker-source-verification.md` §2、§3、§5.1;派活 worker 选型定为 `UIWorker`,理由见"派活 worker 选型"说明):快脑(主 PipelineWorker 的对话分支)只负责判断"这一轮要不要把事情交出去"这一件事——识别到用户提出了一个适合放到后台执行的任务时,通过 `worker.job(...)`(job 机制而非 activation:主导权不转移,快脑仍是本次通话的主导方,verification 文档 §3 实锤)把这一轮请求原样交给 task-dispatch worker(`UIWorker`)。**"派什么活、任务怎么描述、要不要拆成多个并行任务(fan out)"这一层判断完全交给 task-dispatch worker 自带的第二个 LLM 决定**——即"用户口语 → 任务书"的转换责任落在这个第二个 LLM 身上,不再是快脑的职责(该 LLM 是完整的二次推理而非透传:verification 文档 §2 实锤,`_run_llm_turn` 把请求作为 `user` 角色消息注入自己独立的 context 后完整跑一轮 LLM 推理;它本身又是一个带完整 pipeline 与 RTVI 的 root worker,verification 文档 §5.1 实锤)。该第二个 LLM 决定实际派发的具体任务内容后,以 subprocess 方式调用 `openclaw agent` CLI 发起派发(零自研,直接用官方 CLI;`--timeout` 默认 600 秒,可配 `0` 关闭,已实测核对:`openclaw agent --help` 输出确认该默认值)。该调用固有的最长可达 600 秒的阻塞特性,不得体现为主对话的卡顿(具体如何避免阻塞属 S2a 实现取舍,本 FR 只约束可观察的行为结果,见下方判据 1);且用户中途挂断本次通话,不应终止已经在 OpenClaw Gateway 侧运行的任务(呼应 C4)。若 `openclaw agent` 调用本身失败(如 Gateway 不可达、CLI 报错退出——这发生在任务被 OpenClaw 任务状态机接管之前,不同于任务被接管之后 OpenClaw 侧记录的任务终态——后者不会被主动推送过来,只有 FR-2 的用户主动查询才看得到),该失败经标准工具调用报错路径反馈给发起本次调用的 LLM(即 task-dispatch worker 内置的第二个 LLM,pipecat 函数调用的既有机制,零自研),再经既有播报/措辞机制回流告知用户,措辞仍由快脑自行判断(与 C1 处置口径一致),不额外设计专门的报错话术层;OpenClaw Gateway 在本机以 systemd 常驻运行是本次架构的前提假设,不在本 PRD 验收范围内重复验证其可用性。

**验收判据**:
1. Given 用户提出一个触发派活的请求且派活已被发起,When 同一次通话中用户紧接着(不等待派发结果)提出下一个不相关问题,Then 该新问题正常获得回复,响应时长与未发生派活时的基线相当(不等待 `openclaw agent` 进程退出)。观察步骤:优先用测试桩模拟 `openclaw agent` 迟迟不返回,验证同一通话内后续对话轮次不受阻塞;若暂不具备桩测试条件,退化为真实环境下人工触发一次派发后立即追加提问、计时对比派活前后的首字节响应延迟,判定标准为"数量级相当"而非阻塞到接近 600 秒量级(具体延迟阈值数字不在此拍死,需 S2a/QA 依真机基线校准)。本判据是黑盒行为验证,覆盖两级决策链路整体(快脑路由 → 第二个 LLM 决定任务内容 → subprocess 调用),不单独割裂验证某一级是否阻塞。
2. Given 一个任务已成功派发且正在 OpenClaw 侧执行,When 用户在任务完成前主动挂断/断开本次语音连接,Then 在 OpenClaw 侧(不依赖 voice-agent 进程存活)观察到该任务继续运行直至到达终态,而非因语音客户端断开被连带取消。命令:`openclaw tasks show <lookup> --json` 在断连前后各查一次(该子命令已实测核对:`openclaw tasks --help` 输出确认 `show` 可"by task id, run id, or session key"查询),期望断连后任务状态不是 `cancelled`,且能继续演进直至 `succeeded`/`failed`/`timed_out`/`lost` 之一。
3. 回归判据(C2 处置并入):Given 本次改动触及 `prompts.py`/`SYSTEM_PROMPT`,When 改动落地后重跑既有 eval 场景集合(不含本次同步更新的 r4),Then 全部场景保持通过、无新增失败。命令:对 `server/evals/` 下既有场景逐个 `uv run pipecat eval run <scenario>.yaml -v`,或以 manifest 走 `uv run pipecat eval suite`(批量跑法由 S2a 定;注意项目纪律要求启动 bot.py/pytest 带 `NLTK_DISABLE_IMPORT_SECURITY=1`)→ 期望全部 exit code 0。

### FR-2 · 任务状态查询(用户主动询问进展,pull-based)(P0)

**描述**:用户裁决(2026-08-08,s1b 呈批回合,原话「入范围,加一条FR」)——开放问题 1(pull-based 状态查询)入范围。助手接入现成 `openclaw tasks show <lookup>` 与 `openclaw tasks list`(均已实测核对,见下方命令输出),将其封装为一个 LLM 可调用的 function-calling 工具(pipecat 现成机制,零自研),使用户可在通话中随时主动询问某个已派发任务或全部在途任务的当前进展。**该调用是同步短调用**——直接查库返回任务当前快照,不等待任务本身执行完成,与 FR-3(任务完成消息回流播报)里 task-dispatch worker 后台持有的 `openclaw mcp serve` 连接、MCP `events_wait` 长轮询是完全不同的性质:`events_wait` 是"等事件到达才返回"(最长可阻塞 300 秒),因此绝不能写进 LLM 的 function call,只能待在 task-dispatch worker 自己独立的后台 asyncio task 里;而 `tasks show`/`tasks list` 是"立即返回当前状态"的一次性查询,可以安全地作为普通 function call 使用,不会造成对话卡顿——两者不可混为一谈。查询结果的具体措辞同样由快脑自行判断转述,不做二次校验(与 C1 处置口径一致)。若 lookup 不存在或 CLI 报错,复用 FR-1 已定的标准工具调用报错路径反馈给 LLM,不额外设计专门的报错话术层。**本轮实测后的责任划分补充(2026-08-08)**:FR-3 改为不回查任务状态之后,"读取任务的结构化状态(`status`/`terminalSummary` 之类字段)"这件事在本期**只**发生在本 FR 这一条路径上,且**只在用户主动开口问时**发生——系统不会自行触发状态查询。

**命令核对(已实测,本次修订执行验证)**:
```
$ openclaw tasks show --help
Usage: openclaw tasks show [options] <lookup>
Show one background task by task id, run id, or session key

$ openclaw tasks list --help
Usage: openclaw tasks list [options]
List tracked background tasks
Options: --status <name>  Filter by status (queued, running, succeeded, failed, timed_out, cancelled, lost)
```

**验收判据**:
1. Given 用户此前已成功派发过一个任务并持有其 lookup/task id,When 用户在通话中问及该任务当前进展(如"我那个任务现在怎么样了"),Then 快脑触发一次 `tasks show <lookup>` 的工具调用,并在拿到返回结果后据此播报当前状态。命令:`time openclaw tasks show <lookup> --json` 实测确认该调用属同步短调用(经验参考:同类只读查询预期亚秒到个位数秒返回,不同于 `openclaw agent` 可长达 600 秒或 `events_wait` 可长达 300 秒);"是否造成可感知卡顿"的具体阈值由 S2a/QA 依真机基线校准,判定标准是"该调用不使当次响应显著慢于无查询时的基线"。
2. Given 用户想了解全部在途任务而非某一个具体任务,When 用户问及"我现在有哪些任务在跑"类问题,Then 触发 `tasks list`(可选 `--status running` 过滤,该值已确认为合法 `--status` 取值)工具调用并据此转述,能覆盖当前非终态任务的汇总回答。
3. 该工具调用不影响主对话的非阻塞特性:复用 FR-1 判据 1 的验证模式(同一通话内该查询前后追加提问,后续提问正常获得回复)。

### FR-3 · 任务完成消息回流播报(只认结论消息、转述 agent 自述、不回查任务状态;单通道、安全插入窗、并发合并)(P0)

**描述(本轮据真机实测整体改写,2026-08-08)**:本 FR 原描述建立在"OpenClaw 推送任务终态事件"这一前提上,该前提经真机实测**不成立**,原描述整体作废。

**实测事实(证据:数据,`baseline/preflight-live.md` §3.1-§3.3,含实装源码逐处核对与原样事件样本 `baseline/mcp-event-sample.json`)**:
- MCP bridge 的事件类型全集(实装 `dist/mcp-cli-CnI7JKSG.js` 6 处 `enqueue` 逐一核对)为 `message` 一种消息事件 + 5 种审批类事件(`claude_permission_request`、exec 与 plugin 各自的 `_requested`/`_resolved`)——**不存在任何任务生命周期/终态事件类型**;
- 唯一与任务相关的信号是 `type: "message"` 且 `role: "assistant"` 的事件,即 agent 干完活后在会话里说的那句话;其 `sessionKey` 实测**精确等于**本项目派发时自行生成的那个会话键(生成规则属契约层,PRD 不拍定),可直接用作关联锚点;
- 该 assistant 事件里读不出任何 OpenClaw 原生终态字符串:`raw.status` 实测为会话级的 `"running"`,是消息产出瞬间的会话状态,不是任务终态。

**本轮补测新增的实测事实(证据:数据,`preflight-live.md` §8 与 §10 D-10,原样样本 `baseline/failure-path-samples.json`;8 次真派发)**:
- `role=assistant` 的事件**不是只有一种形态**。按 `raw.message.stopReason` 实测分三态:`toolUse`(两个子形态——工具调用消息,顶层**连 `text` 键都没有**、文本在 `raw.message.content` 内;以及"边干边说"的过程播报,`text` 是一句自然语言中间话)、`stop`(收尾结论,**只有这一条是要播的**)、`aborted`(被中止瞬间,`text` 实测为空串 `''`,另带 `raw.message.errorMessage`)。
- 两份原样样本合计 19 条 assistant 事件的分布:`toolUse` 13 条、`stop` 4 条、`aborted` 2 条,**无一条缺 `stopReason` 键**;`role=user` 事件的 `raw.message` 则根本没有这个键(主会话直接从样本 JSON 逐条提取 `raw.message` 统计,复核方式见判据 5)。
- 不筛选的直接后果(实测反例):F4b 一次派发产生 5 条 assistant 事件(4 条 `toolUse` + 1 条 `stop`),F7b 产生 3 条(2 条 `toolUse` + 1 条 `aborted`)——"收到 assistant 事件就转述"会把工具调用中间过程当结论播、同一个任务播好几次,超时那次还会播出一段空内容。

**新形态(用户裁决,2026-08-08 实测后,原话「人家已经给你报了你还确认啥,只要知道什么任务完毕就行了,任务结果正常都会有制定文件对应啥的」)**:task-dispatch worker 的后台事件循环收到属于本次派发会话键、**且 `raw.message.stopReason` 等于 `"stop"`** 的 `role=assistant` 消息事件后,**把该事件里 agent 说的那句话(`event.text`)直接作为素材注入给快脑转述,不回查任务状态、不解析任何结构化状态字段**;`stopReason` 取其他值(实测为 `toolUse`/`aborted`)或该键缺失的 assistant 事件**一律丢弃**——不播报、不注入、不计入任何后续判断。**这里读 `stopReason` 不构成"解析结构化状态"**:它是消息本身的收尾标记(判"这条话说完了没有"),不是任务终态字段(`status`/`terminalSummary` 本期仍不读,见非目标条目 9)。该形态与硬约束 C1 同向(完成真实性归 OpenClaw,本项目不核验、不改写其转述);"主动查询任务状态"的能力并未因此丢失——它由 FR-2 承载,用户在通话中开口问才查。

**沿用不变的约束(与原描述一致,实测未推翻)**:
- `events_wait` 长轮询(默认 30 秒、单次上限 300 秒,实装常量 `EVENTS_WAIT_TIMEOUT_LIMIT_MS`)绝不能写进 LLM 的 function call——会卡住那一轮对话最长 300 秒;必须待在 task-dispatch worker 自己独立的后台 asyncio task 里。
- 播报走既有素材注入路径(复用 R3 Producer/Consumer 机制,与慢脑回流同构),在下一个安全插入窗口(无正在播报的语音、用户未在说话)自然带出,不新开输出通道(呼应 C3)。多个待播报素材同时到达时合并或排队播报,不允许相互打断/抢话。
- 播报的具体措辞、如何转述完全由快脑自行判断,本项目不做二次校验或改写(C1 口径,不在此重复设约束)。实测补充:agent 那句话可能很长(样本实测 656 / 657 字符),要不要摘要、怎么说同属快脑措辞判断范畴,本 FR 不设长度类判据。

**已知边界(显式不覆盖,非缺陷)**:MCP bridge 的事件队列是每个 `openclaw mcp serve` 进程各自的 live-only 内存队列(cursor 从 1 起自增、上限 1000 条滚动丢弃),**连接建立之前发生的事件取不回**(实测:新起连接后 `events_poll(after_cursor=0)` 返回 0 条,此前任务的历史事件全部捞不回)。两条直接后果:①bridge 必须在派发之前就连上并开始消费,否则整个任务的事件会全部漏掉;②voice-agent 进程重启期间到达的消息事件不保证被本机制捕获,本 PRD 不要求覆盖重启空窗(与非目标 2 "不做持久化"口径一致),只要求进程正常存活期间的监听按下方判据生效。

**验收判据**:
1. ### FR-4 · 多任务状态互不串扰(P1)

**描述**:用户可在同一通话中先后派发多个独立任务;每个任务回流的消息都必须关联到各自的任务标识,不发生张冠李戴(如 A 任务的完成播报被误认成 B)。**本轮实测后的关联锚点明确化(2026-08-08)**:关联依据是事件的 `sessionKey`——实测它精确等于派发时自行生成、且本身即可作为 `tasks show` lookup 的那个会话键(`preflight-live.md` §2:任务记录里的 `childSessionKey`/`ownerKey`/`requesterSessionKey` 三者都与之**相等**,不是前缀/后缀关系),MCP 侧的 `session_key` 过滤也是精确相等匹配;本 FR 不依赖任何任务终态事件(那类事件不存在,见 FR-3)。

**验收判据**:Given 用户先后派发任务 A 与任务 B(各自持有独立的会话键/task id),When A 的 agent 结论消息事件(`stopReason="stop"`)先到达、B 仍在执行中(尚未产生 `stopReason="stop"` 的结论消息事件),Then 播报给用户的完成消息明确关联到 A 而非 B,且不产生"B 也已完成"之类的误报;验收侧另用 `openclaw tasks show <lookup_A>`/`openclaw tasks show <lookup_B>`(或 `openclaw tasks list`)独立核对两者状态各自独立——A 已是终态、B 仍处于非终态,互不影响。**注**:此处的 `tasks show` 是**验收侧的外部核对手段**,不是产品运行路径上的回查,与 FR-3"不回查任务状态"不冲突;该命令的读法见 `preflight-live.md` §4 D-1(`--json` 的 JSON 实际落在 stderr,命中与未命中只能靠 exit code 区分)。

### FR-5 · 手动接管可达性(P1)

**描述**:派发产生的任务应对应 OpenClaw 里一个可被人工直接接管的会话(而非匿名一次性调用),使用户在需要时可以绕开语音、直接在 OpenClaw 自己的渠道里接管对话——该能力零自研(OpenClaw 会话天然如此,`openclaw-reference.md` §4.1 源码+文档双重实锤:OpenClaw 调度产生的会话落盘于顶层 `<uuid>.jsonl`、无 `subagents/` 子目录,与人工手动跑的会话同构同位),要求只是派活时对 `openclaw agent` CLI 的调用方式不能破坏这一前提(如误用了不产生可寻址会话的调用模式)。

**验收判据**:
- 必测(不依赖额外渠道凭据):Given 一次通过本系统发起的派发,When 用 OpenClaw 自身工具查询该次派发对应的会话(如 `openclaw tasks show <lookup>` 关联的 session key/id),Then 能得到一个具体、非空的会话标识,证明它不是匿名/一次性调用。
- 可选加测(若本机 OpenClaw 已配置可用的 IM 渠道,不为此专门新增渠道凭据):Given 该渠道已配置可用,When 在该渠道向上述会话标识对应的会话发一条消息,Then 该消息确实路由到了同一个 session(而非无响应或路由到别处)。是否执行这一层由 S2a/QA 视现有渠道配置情况决定,PRD 不强制(避免为验收目的新增外部渠道凭据这类操作性开销)。

**本轮实测补充(2026-08-08)**:`preflight-live.md` §2 已实测确认必测项可满足——四次真派发的任务记录里 `childSessionKey`/`ownerKey`/`requesterSessionKey` 三者均非空,且都等于派发时使用的会话键;该会话键直接作为 lookup 传 `tasks show` 亦 exit=0 命中。
